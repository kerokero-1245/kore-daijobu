# これ、大丈夫？ — 設計ドキュメント

> 高齢の親が「怪しい電話・訪問・SMS」に出くわしたとき、大きなボタン1つで子にすぐ相談できる詐欺対策アプリ。

最終更新: 2026-07-11

---

## 1. コンセプト

詐欺は「**急がせて・一人で・その場で決めさせる**」ことで成立する。
この3点のうち「一人で」を崩す = **家族が判断に関わる瞬間を割り込ませる**のがこのアプリの狙い。

- 番号データベースで技術的にブロックする既存方式（DBの規模が競争力＝個人開発では不利）とは戦わない。
- 警察も推奨する「一人で判断せず家族に相談」を、**文字入力ゼロ・ワンタップ**で仕組み化する。

### 立ち位置（重要・法的配慮）
- このアプリは **「緊急通報」ではなく「相談・気づきの補助」**。
  「緊急通報」を名乗ると責任・信頼性の要求が跳ね上がるため、UI・説明文でも明確に「相談ツール」と位置づける。
- 「必ず詐欺を防げる」等の断定表現はしない。

---

## 2. 登場人物（ロール）

| ロール | 誰 | 役割 | UIの方針 |
|---|---|---|---|
| **親** | 高齢の親 | 相談を送る側 | 極限までシンプル。1画面1操作・文字大・文字入力ゼロ |
| **子** | 依頼者（あなた） | 相談を受けて答える側 | 普通のアプリUIでOK。素早く返信できること優先 |

MVPは **親1 ↔ 子1 の1対1**。ただしデータ設計は将来「複数家族が受け取る」に拡張できる形にする。

---

## 3. MVP スコープ

### コアループ（これ1つを作り切る）
```
親が「これ、大丈夫？」を押す
  → 種類を選ぶ（＋任意で写真1枚）
  → 子にプッシュ通知
  → 子が返信（定型文＋自由入力）
  → 親の画面に答えが大きく表示される
```

### やること（MVPに入れる）
- 親：相談ボタン → 種類選択 → 送信 → 「相談中…」→ 返信表示
- 子：プッシュ受信 → 相談内容確認 → 定型文/自由入力で返信
- 招待コードによるペアリング（子が発行 → 親が入力 or QR）
- 相談履歴の一覧（子側）

### やらないこと（MVPでは入れない = 次段階）
- 複数家族への同報
- 通話中の自動検知・着信ブロック（技術的に重い／OS制約）
- 音声・ビデオ通話（既存の電話でよい）
- AIによる詐欺判定（まずは人＝子が判断）
- 位置情報・見守り機能

## 4. 画面の流れ

### 親側（文字入力ゼロ）
```
[ホーム]
  大ボタン「これ、大丈夫？」
  （下に小さく「◯◯（子）に相談できます」）
     │ タップ
     ▼
[種類を選ぶ]  ※大きなボタンを縦並び
  ・お金の話
  ・還付金・税金
  ・点検・工事・リフォーム
  ・家族や役所を名乗る電話
  ・その他
     │ タップ
     ▼
[写真（任意）]  「ハガキやSMSがあれば撮る」＋「そのまま送る」
     │
     ▼
[相談中…]  「◯◯に相談しています」＋ぐるぐる
     │ 子が返信すると自動で
     ▼
[答え]  例) ⚠️「それ詐欺かも。対応しないで」
        大きな文字＋色分け（危険=赤 / 大丈夫=緑 / 確認中=黄）
```

### 子側
```
[プッシュ通知]「親から相談：お金の話」
     │ タップ
     ▼
[相談詳細]  種類・時刻・写真
     │
     ▼
[返信]  定型文をタップ：
  ・「それ詐欺！絶対に対応しないで」
  ・「一旦電話を切って。あとでかけ直すね」
  ・「大丈夫、それは本物だよ」
  ＋自由入力欄
     │ 送信
     ▼
[送信完了]  親側にリアルタイム反映
```

## 5. データモデル（Supabase / Postgres 想定）

```
users
  id            (uuid, PK)
  role          ('parent' | 'child')
  display_name  (text)          -- 「お母さん」「たろう」など
  push_token    (text)          -- Expo push token
  created_at

pairs                            -- 親と子の繋がり（MVPは1本）
  id            (uuid, PK)
  parent_id     (uuid → users)
  child_id      (uuid → users)
  invite_code   (text)          -- ペアリング用
  status        ('pending' | 'active')
  created_at

consultations                    -- 相談1件
  id            (uuid, PK)
  pair_id       (uuid → pairs)
  category      (text)           -- 'money' | 'refund' | 'construction' | 'impersonation' | 'other'
  photo_url     (text, null可)
  status        ('waiting' | 'answered')
  created_at

replies                          -- 相談への返信
  id            (uuid, PK)
  consultation_id (uuid → consultations)
  verdict       ('danger' | 'safe' | 'unsure')  -- 色分け用
  message       (text)
  created_at
```

将来の複数家族対応は `pairs` を「1親 : N子」に拡張、`consultations` を全員に配信して最初の返信を採用、で対応可能。

## 6. 技術構成

| 役割 | 技術 | 補足 |
|---|---|---|
| アプリ | **Expo (React Native + TypeScript)** | iOS/Android 単一コード。Expo Go で実機テスト |
| バックエンド | **Supabase** | Postgres + リアルタイム購読 + 認証 + Edge Functions（無料枠・カード不要） |
| リアルタイム同期 | Supabase Realtime | 返信を親画面へ即反映（`answered` を購読） |
| プッシュ通知 | **Expo Push** + Supabase Edge Function | 相談作成時に相手へ送信 |
| ペアリング | 招待コード（6桁）/ QR | 親はアカウント作成不要 |

> 代替案：Firebase（Firestore + Cloud Messaging）。realtimeは同等に簡単だが、
> サーバー側プッシュに Blaze（課金）プランが要るため、無料で始めやすい Supabase を第一候補にする。

### 開発環境メモ
- Node は **v20 または v24**（nvm）で。macOS 既定の v16 だと Expo が動かない。

## 7. ロードマップ（作る順番）

1. **プロジェクト雛形** … Expo アプリ + Supabase プロジェクト作成、DB定義
2. **親ホーム → 種類選択 → 送信**（まずローカルで画面だけ）
3. **Supabaseに保存 → 子側で一覧表示**（データが繋がる）
4. **子が返信 → 親にリアルタイム反映**（コアループ完成）
5. **プッシュ通知**（相談・返信を通知）
6. **招待コードでペアリング**
7. **親UIの磨き込み**（文字大・色分け・迷わない導線）
8. 実機で親役・子役に分けて実地テスト

MVPは 1〜4 が出来た時点で「動くもの」になる。

## 8. 準備が必要なもの（あなた側）

- ※将来 App Store / Google Play に本番公開する段階で、Apple Developer（年約$99）等が必要。テスト段階は不要。
