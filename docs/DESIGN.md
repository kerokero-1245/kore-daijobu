## 1. コンセプト

詐欺は「**急がせて・一人で・その場で決めさせる**」ことで成立する。
この3点のうち「一人で」を崩す = **家族が判断に関わる瞬間を割り込ませる**のがこのアプリの狙い。

- 番号データベースで技術的にブロックする既存方式（DBの規模が競争力＝個人開発では不利）とは戦わない。
- 警察も推奨する「一人で判断せず家族に相談」を、**文字入力ゼロ・ワンタップ**で仕組み化する。

### 立ち位置（重要・法的配慮）

- このアプリは **「緊急通報」ではなく「相談・気づきの補助」**。
  「緊急通報」を名乗ると責任・信頼性の要求が跳ね上がるため、UI・説明文でも明確に「相談ツール」と位置づける。
- 「必ず詐欺を防げる」等の断定表現はしない。

## 2. 登場人物（ロール）

| ロール | 誰               | 役割                 | UIの方針                                           |
| ------ | ---------------- | -------------------- | -------------------------------------------------- |
| **親** | 高齢の親         | 相談を送る側         | 極限までシンプル。1画面1操作・文字大・文字入力ゼロ |
| **子** | 依頼者（あなた） | 相談を受けて答える側 | 普通のアプリUIでOK。素早く返信できること優先       |

MVPは **親1 ↔ 子1 の1対1**。ただしデータ設計は将来「複数家族が受け取る」に拡張できる形にする。

## 3. MVP スコープ

### コアループ（これ1つを作り切る）

```
親が「これ、大丈夫？」を押す
  → 種類を選ぶ（＋任意で写真1枚）
  → 子にプッシュ通知
  → 子が返信（定型文＋自由入力）
  → 親の画面に答えが大きく表示される
```

### やること（MVPに入れる）

- 親：相談ボタン → 種類選択 → 送信 → 「相談中…」→ 返信表示。ホームに最近の相談の入口（最大3件）
- 子：プッシュ受信 → 相談内容確認 → 定型文で返信、または自由入力（200字まで）＋判定を選んで返信
- 招待コードによるペアリング（子が発行 → 親が入力 or QR）
- 相談履歴の一覧（子側）

### やらないこと（MVPでは入れない = 次段階）

- 複数家族への同報
- 通話中の自動検知・着信ブロック（技術的に重い／OS制約）
- 音声・ビデオ通話（既存の電話でよい）
- AIによる詐欺判定（まずは人＝子が判断）
- 位置情報・見守り機能

## 4. 画面の流れ

### 最初の 1 回（役割とペアリング）

```
[どちらのスマホ？]  「親のスマホ」/「子のスマホ」  ※選んだ役割はあとから変えない（開発用の「最初からやり直す」と、ホームの「つなぎ直す」で新しい利用者になるときだけ）
     │
     ├─ 子 ─▶ [番号を出す]  6 桁を大きく＋残り時間（10 分）＋「新しい番号を出す」
     │                        │ 親のスマホで番号が入ると自動で
     │                        ▼
     │                      [受信一覧]
     │
     └─ 親 ─▶ [番号を入れる]  数字キー 0〜9 と「消す」。はじめの設定として子が親のスマホで打つ
                              失敗は 1 文で出す（期限切れ・使用済み・ちがう番号・回数が多すぎる）
                              │ 6 桁そろうと自動で送り、つながると
                              ▼
                            [ホーム]
```

### 親側（文字入力ゼロ）

```
[ホーム]
  （まだ開いていない答えがあれば、大ボタンより上に「答えが届きました」の入口）
  大ボタン「これ、大丈夫？」
  （下に小さく「◯◯（子）に相談できます」）
  （その下に「さいきんの相談」の入口。返事待ち・確認ずみの答え）
  ※入口は合わせて最大3件。並びは 未読の答え → 返事待ち → 確認ずみの答え（それぞれ新しい順）
  ※「1画面1操作」の例外：入口は届いた答えを見るための補助で、主操作の大ボタンは常に1つ
     │ 大ボタンをタップ（入口をタップすると、その相談の[相談中…]か[答え]へ）
     ▼
[種類を選ぶ]  ※大きなボタンを縦並び
  ・お金の話
  ・還付金・税金
  ・点検・工事・リフォーム
  ・家族や役所を名乗る電話
  ・その他
     │ タップ
     ▼
[写真（任意）]  「ハガキやSMSがあれば撮る」＋「そのまま送る」  ※未実装（いまは種類を選ぶとすぐ送られる）
     │
     ▼
[相談中…]  「◯◯に相談しています」＋ぐるぐる＋「ホームにもどる」
     │ 子が返信すると自動で（ホームに戻っていても、ホームの入口から答えを開ける）
     ▼
[答え]  例) ⚠️「それ詐欺かも。対応しないで」
        大きな文字＋色分け（危険=赤 / 大丈夫=緑 / 確認中=黄）＋「ホームにもどる」
        長い返信はスクロールで読む（見出しは最初から見える位置）
```

### 子側

```
[プッシュ通知]「親から相談：お金の話」
     │ タップ
     ▼
[相談詳細]  種類・時刻・写真
     │
     ▼
[返信]  定型文をタップ：
  ・「それ詐欺かも！絶対に対応しないで」
  ・「一旦電話を切って。あとでかけ直すね」
  ・「大丈夫、それは本物だよ」
  ＋自由入力欄（200字まで）
    → 判定（詐欺かも / 大丈夫そう / まだ分からない）を選ぶ。文面と判定がそろうまで送れない
      （そろっていないときは理由を画面に出す。親の見出しはこの判定で決まる）
     │ 送信
     ▼
[送信完了]  親側にリアルタイム反映
```

## 5. データモデル（Supabase / Postgres）

表・制約・RLS・招待の関数・返信のトリガーの正本は [supabase/migrations/](../supabase/migrations/)（`20261016000000_init.sql` と Realtime の `20261016000001_realtime.sql`）。要点:

- 表は profiles（auth.users と同じ id・役割）/ pairs（子が pending で作り、招待の引き換えで active）/ pair_invites・invite_attempts（招待と試行。クライアントからは読めない）/ consultations / replies / push_tokens / push_log
- 守りは DB に置く（anon key はアプリに入るため）。全表に RLS を掛け、自分のペアの当事者だけが読める。相談を作れるのは親、返信できるのは子だけ
- status は列の grant から外し、返信の挿入トリガーだけが answered にする（「返信あり・返事待ち」を DB でも作れない。画面の判別共用体と同じ不変条件）
- 招待は `create_invite()` / `redeem_invite(code)` の関数だけで扱う（6 桁・10 分・使い切り・失敗が 10 分で 5 回に達したら断る）
- アプリは `src/data/backend.ts` の窓口だけを使い、開発中に Supabase の設定が無いときは同じ規則の偽バックエンド（`src/data/fakeBackend.ts`）で動く。行は `src/domain/row.ts` で読み、status と返信の組が合わない行は捨てる
- 相談の id はアプリが作り、先に手元へ足してから送る。送れなければ手元を戻す。相手の変化は Realtime（consultations と pairs）で受け、起動時と前面に戻ったときに最近 50 件を取り直す
- セッションは iOS / Android では暗号化して端末に置き（鍵は SecureStore）、Web には SecureStore が無いので localStorage に平文で置く（ブラウザの保存域は同じオリジンからしか読めず、暗号化しても鍵を同じ場所に置くことになるため）

将来の複数家族対応は `pairs` を「1親 : N子」に拡張、`consultations` を全員に配信して最初の返信を採用、で対応可能。

## 6. 技術構成

| 役割             | 技術                                   | 補足                                                                                                              |
| ---------------- | -------------------------------------- | ----------------------------------------------------------------------------------------------------------------- |
| アプリ           | **Expo (React Native + TypeScript)**   | iOS/Android 単一コード。Expo Go で実機テスト（プッシュ通知は SDK 53 以降の Expo Go では試せず、開発ビルドが要る） |
| バックエンド     | **Supabase**                           | Postgres + リアルタイム購読 + 認証 + Edge Functions（無料枠・カード不要）                                         |
| リアルタイム同期 | Supabase Realtime                      | consultations の変更と pairs の更新を 1 本のチャンネルで購読し、親と子の画面へ即反映                              |
| プッシュ通知     | **Expo Push** + Supabase Edge Function | 相談は子へ、返事は親へ。Database Webhook → Edge Function `notify` → Expo Push（実機での到達は未確認）             |
| ペアリング       | 招待コード（6桁）/ QR                  | 親はアカウント作成不要                                                                                            |

> 代替案：Firebase（Firestore + Cloud Messaging）。realtimeは同等に簡単だが、
> サーバー側プッシュに Blaze（課金）プランが要るため、無料で始めやすい Supabase を第一候補にする。

### プッシュ通知

- 送る側は `supabase/functions/notify/`。中身の `core.ts` は Deno にも Node にも依存せず（fetch・時計・DB は引数で受ける）、`tests/notify.test.mjs` で検査する。Deno の入口 `index.ts` は秘密のヘッダ（`NOTIFY_WEBHOOK_SECRET`）を確かめ、service role の client を渡すだけ
- consultations の INSERT なら子へ、UPDATE で waiting → answered になったら親へ送る（宛先は pairs の行から）。答えを開いた印の UPDATE では送らない。本文は断定の語を使わない
- 送れなかったとき: 通信失敗・429・5xx は 1 秒・2 秒・4 秒と間を広げて 3 回まで再試行、400 は再試行しない。DeviceNotRegistered のトークンは disabled_at を埋め、以後は送らない。ticket は 1 件ずつ push_log に残す（届いたかの receipt は見ない）
- アプリは開発ビルドの実機でだけ、つながったあとにトークンを取って push_tokens に upsert する（`src/data/pushTokens.native.ts`。Web 版の `pushTokens.ts` は expo-notifications を読まずに何もしない）。通知を押すと、親は答えの画面、子は相談の詳細を開く。サインアウトの前に自分のトークンの行を外す（token が主キーで、自分の行しか書けないため）
- プッシュは補助の経路で、正本は DB。画面は Realtime と起動時・前面復帰の取り直しで追いつく

### 送れなかったとき

- 送れなかったときは手元を戻し、親の画面に「つながっていません。電話で直接きいてね」を出す（既読の送信失敗だけは手元を戻さない。戻すと答えの画面が送り直しを続けるため）
- 親には文字入力を求めない。同じ文言を子の相談詳細の画面にも出す（`src/components/SyncErrorNotice.tsx`。一覧を取り直せたら消える）。子の受信一覧の最上部にも出す（返信の失敗は詳細から一覧へ戻ったあとに見える）
- 一覧の取り直し（起動時・前面復帰・購読のつなぎ直し）に失敗したときも、手元の一覧はそのままで同じ文言を出す

### 設定の扱い（本番の書き出し）

- バックエンドの選び方は `src/data/chooseBackend.ts`。URL と anon key がそろえば Supabase、偽物は開発中（`__DEV__`）で設定が無いときか `EXPO_PUBLIC_BACKEND=fake` を明示したときだけ
- 本番の書き出しで設定が欠けていればバックエンドを作らず、起動画面に「設定がありません」を出す（「もう一度」は出さない）。偽物で動くと、送れたように見えて相手に届かないため
- 一度サインインした端末には印を置き、保存したセッションが読めないときは新しい匿名ユーザーを作らずに起動画面のエラーにする（作ると元のペアから黙って外れる）。新しく作るのは、印が無いときと自分でサインアウトしたあとだけ。起動画面のエラーには「つなぎ直す」を出し、押すと新しい利用者として始め直せる

### つなぎ直す

- 親のホームと子の受信一覧の一番下に小さく「つなぎ直す」を置く。押すと 1 回だけ確かめ、サインアウトして新しい匿名ユーザーで役割の選択から始める（`src/components/RepairLink.tsx`）
- 両方の端末で押して、もう一度番号で結ぶ。前の相談は見えなくなる。前のペアは DB に残る（解除の関数は作っていない。将来の予定）

### 開発環境メモ

- Node は `.nvmrc` の版（24 系。nvm で切り替え）。react-native 0.86 の `engines` は 24 系なら 24.3.0 以上を求める。macOS 既定の v16 だと Expo が動かない。

## 7. ロードマップ（作る順番）

1. **プロジェクト雛形** … Expo アプリ + Supabase プロジェクト作成、DB定義（済: アプリと移行 SQL。Supabase プロジェクトの作成はまだ）
2. **親ホーム → 種類選択 → 送信**（まずローカルで画面だけ）（済）
3. **Supabaseに保存 → 子側で一覧表示**（データが繋がる）（済: 偽バックエンドの 2 タブで確認。本物の Supabase ではまだ）
4. **子が返信 → 親にリアルタイム反映**（コアループ完成）（済: 同上）
5. **プッシュ通知**（相談・返信を通知）（済: Edge Function・トークンの保存・通知から開く。本物の Supabase と実機ではまだ）
6. **招待コードでペアリング**（済: 6 桁の番号。QR はまだ）
7. **親UIの磨き込み**（文字大・色分け・迷わない導線）
8. 実機で親役・子役に分けて実地テスト

MVPは 1〜4 が出来た時点で「動くもの」になる。
